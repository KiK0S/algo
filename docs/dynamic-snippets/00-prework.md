# Dynamic Snippet Pre-Work Plan

## Goal

Build shared extension infrastructure so every solver or brick can be rendered from a dynamic recipe instead of a single static header paste. The system should let the insertion pipeline choose sections, optional features, dependencies, existing variable names, and exported names.

## Current Status After Initial Migrations

The shared infrastructure is good enough for full single-solver migrations:

- `CatalogEntry.generator` accepts arbitrary generator ids.
- Generator dispatch uses a registry instead of hard-coded generator branches.
- `createNamePlanner` provides shared collision-aware name reservation.
- Renderers can return section-based `RenderedRecipe` objects, and the
  composer emits sections in the target assembly order.
- `/solvers/berlekamp_massey`, `/solvers/sparse_table`, and `/solvers/dsu` are
  completed dynamic solver migrations with catalog metadata, extension tests,
  solver-path C++ tests, static fallbacks under `lib/solvers/`, and removed
  top-level compatibility headers.

Remaining pre-work such as richer C++ role analysis, in-place/full-solution
composition, generated dependency rendering through one shared planner, and
reusable form primitives can be added inside the next solver migration when
that solver needs it. Do not wait for all pre-work phases to be finished before
migrating the next solver.

## Assumptions

- `lib/` remains the source of truth, and `extension/library/` stays generated by `npm --prefix extension run build`.
- Static snippet insertion must keep working during migration, but top-level compatibility headers are not part of the final state.
- Solvers should remain usable as global paste snippets unless the user explicitly chooses full-solution generation.
- Dynamic recipes can emit empty sections, but they must still use the common section model.
- Existing document analysis should be extended rather than replaced.
- Every reusable artifact is ultimately classified as either `solver` or `brick`.

## Settled General Alignment

The general migration defaults have been confirmed with the user and are
recorded in [README.md](./README.md#settled-migration-defaults). Future agents
should not ask those general questions again. Ask only solver-specific questions
that are not covered by the settled defaults or the assigned solver plan.

## Agent Posture

Use this file as infrastructure reference, not as a reason to stop after a small
infrastructure task. The expected next step is to pick one todo solver, add any
missing shared helper needed by that solver, and complete that solver's
migration before handing off.

## Questions To Align With The User First

These were the original pre-work questions. Treat them as already answered by
the settled defaults unless a specific implementation detail is still genuinely
blocked:

- Should top-level `lib/*.hpp` compatibility headers be deleted in one cleanup PR or removed gradually as each solver/brick replacement lands?
- Should full-solution generation include `base_template` by default, or should it be a separate explicit pipeline choice?
- Should dynamic solvers default to global paste fragments or full solution files?
- Should generated code keep the current terse contest style, or should renderer output be more class-like for some domains?
- Should interval parameters default to inclusive `[l, r]`, half-open `[l, r)`, or ask per solver?
- Should optional dependencies be inserted as generated dynamic code, static snippets, or both depending on the pipeline?

## Phase 0: Legacy Classification And Removal

Before broad renderer work, make the repository shape unambiguous:

- Treat top-level `lib/*.hpp` files as the legacy compatibility layer.
- Add a catalog classification for every artifact: `solver` or `brick`.
- Create missing `lib/solvers/*.hpp` or `lib/bricks/*.hpp` entries for top-level-only headers.
- Update tests to include the solver/brick paths instead of top-level headers.
- Keep temporary forwarding files only during migration, with an explicit removal issue/checklist.
- Remove top-level compatibility headers once tests and extension sync no longer reference them.

See [03-legacy-cleanup.md](./03-legacy-cleanup.md) for the inventory and classification plan.

## Phase 1: Catalog Schema

Extend `CatalogEntry` in `extension/src/core.ts`:

- Change `generator?: "segtree" | "compress_unique" | "read_vector"` to `generator?: string`.
- Add optional `features`, `sections`, `variants`, and `pipeline` metadata.
- Add conditional exports, for example exports only produced when a feature is enabled.
- Add optional `source` for static fallback and `dynamicSource` or `recipe` when the renderer is not tied to one `.hpp`.
- Keep old catalog entries valid.

Suggested metadata shape:

```json
{
  "path": "/solvers/sparse_table",
  "kind": "solver",
  "insertMode": "global",
  "generator": "sparse_table",
  "features": ["min", "max", "custom", "product", "disjoint"],
  "sections": ["data", "helpers"],
  "exports": ["SparseTable"]
}
```

## Phase 2: Shared C++ Analysis

Extend `analyzeCppDocument` so forms can reuse known surrounding names:

- Detect solution sections: includes, defines, constants, globals, helper area, `solve`, and `main`.
- Detect scalar inputs, vector inputs, strings, matrices, adjacency lists, edge lists, and common aliases.
- Preserve current `// edulcni:const` and `// edulcni:input` annotations.
- Add optional explicit annotations for graph and array roles, for example `// edulcni:graph`, `// edulcni:array`, `// edulcni:string`.
- Report scope enough to distinguish globals from locals in `solve`.
- Keep collision scanning comment/string safe.

## Phase 3: Name Planner

Replace solver-specific name planners with a generic planner:

- `createNamePlanner(analysis)` returns an object that reserves identifiers.
- It can reserve one name, a group of related names, or feature-conditioned names.
- It can prefer existing symbols, for example `n`, `m`, `a`, `g`, `s`, `root`.
- It can expose suggestions to forms while still allowing custom names.
- It must record final exported names for collision summaries.

`planSegmentTreeNames` should become a wrapper around this generic planner.

## Phase 4: Recipe And Section Composer

Introduce a renderer API that returns structured sections:

```ts
interface RenderedRecipe {
  sections: Partial<Record<SolutionSection, string[]>>;
  exports: string[];
  dependencies: DynamicDependency[];
}
```

Composer behavior:

- Keep the existing global insertion behavior for simple paste snippets.
- Add a full-solution mode that emits sections in the target assembly order.
- Add an in-place mode that can insert helpers globally and statement snippets at the cursor.
- Normalize blank lines between sections.
- Apply identifier renames after all selected sections and dependencies are composed.

## Phase 5: Generator Registry

Replace hard-coded generator branches in `extension/src/extension.ts` with a registry:

- each generator provides `prompt`, `render`, and optionally `defaultOptionsForTests`.
- direct commands can still point to generator paths.
- browsing catalog entries can dispatch through the same registry.
- generated dependencies are supported, not rejected, when a dependency renderer is available.

Initial registry entries:

- `segtree`
- `compress_unique`
- `read_vector`
- `sparse_table`
- `lca`
- `suffix_array`

## Phase 6: Form Primitives

Add shared prompt helpers:

- pick existing or custom identifier
- pick existing or custom size expression
- pick existing vector/string/graph/matrix
- pick value type and container type
- pick interval convention
- pick optional features with defaults
- ask whether to declare/read data or use an existing variable

Every form should show existing symbol candidates first.

## Phase 7: Generated Dependency Handling

Allow dynamic solvers to request dependencies by feature:

- LCA RMQ mode can request sparse table.
- Suffix array LCP RMQ can request sparse table.
- Graph solvers can request read-graph data sections when the user wants generated input.
- Full-solution mode can request `base_template`.

Dependency rendering must share one name planner so dependencies and the main solver do not collide.

## Phase 8: Tests And Migration Harness

Add tests in `extension/test/core.test.js` or nearby:

- section composition preserves assembly order.
- generic name planner reserves names across dependencies.
- generated dependency sections are rendered once.
- generated snippets compile for one minimal option set per migrated solver.
- static insertion still applies exported-name collision renames.

Keep focused C++ tests for existing static solvers while dynamic renderers are added.

## Definition Of Done

- Existing segtree, compress_unique, and read_vector behavior still works.
- At least one non-segtree solver can be rendered from the registry using shared form and section primitives.
- Static solver and brick insertion still works through `lib/solvers/` and `lib/bricks/`.
- No extension path, catalog entry, README example, or test depends on top-level `lib/*.hpp` compatibility headers.
- Extension build syncs catalog and dynamic source as before.
- README or extension README documents the new dynamic pipeline at a high level.
